# Multi-language support (i18n)

**Status:** approved 2026-10-10, in progress. This comes before launch item #4 (deploy).

**Languages:** English (`en`), European Portuguese (`pt-PT`) and Brazilian
Portuguese (`pt-BR`). The two Portuguese variants are separate choices in the
picker. Adding another language later means adding translation files, with no
code changes.

## Who sees which language

| What | Language used |
| --- | --- |
| The app's screens (web and Windows app) | **The signed-in person's** choice, saved on the server so it follows them to any till or browser. Before they choose: the last language used on that device, then the computer's language (`pt-BR` → Brazilian, any other `pt` → European), then English. |
| Login, sign-up and password-reset pages | The device's last language, or the computer's. A picker sits in the corner. |
| Receipts, quotes, invoices, the customer display, receipt emails | **The business's** language (Settings → Business). They go to the shop's customers, not to the cashier. |
| Emails to staff (verify email, reset password, invite) | The recipient's language when known, otherwise the business's. |
| Error messages from the server | The language the app is showing. The app sends it with every request. |
| Windows installer | Chosen at the start of the install (English or Portuguese). |
| Windows app first-start screen | The computer's language. |

**Numbers, money and dates** follow the language: `1.234,56 €` and `11/10/2026`
in Portuguese, `€1,234.56` and `10/11/2026` in English. The currency is always
the one set in Settings.

## How it's built

- **Web (`apps/web`):** i18next and react-i18next.
  - Text lives in `src/locales/<language>/<area>.json`, one file per area
    (`common`, `pos`, `products` and so on), loaded with the app. Nothing is
    downloaded later, so it works offline.
  - TypeScript checks every key against the English files, so a typo or a
    missing key fails the build.
  - A test checks that every language has exactly the English keys and the
    same `{{placeholders}}`.
  - Form validation messages are keys, translated where they're shown.
  - All money and date formatting goes through helpers that use the current
    language.
- **API (`apps/api`):**
  - `User.language` (nullable) and `Business.language` (default `en`),
    added in one migration.
  - `PATCH /users/me/language` sets the person's language. The business
    language is set through the existing `PATCH /businesses/me`.
  - The exception filter translates messages using the request's
    `X-Language` header, from a dictionary keyed by the English message.
    The places that throw errors stay unchanged, and a message missing from
    the dictionary stays in English.
  - Email templates exist in all three languages.
- **Desktop (`apps/desktop`):**
  - The NSIS installer is multi-language.
  - `static/setup.html` (choosing the server) picks its text from the
    computer's language.
  - Customer-display text uses the business language.

## Steps

1. **Foundation.** Install the library, add the language detection order
   above, the picker (user menu, This device, and the login page corner),
   and the server columns and endpoint. Convert the shell: sidebar, top
   bar, login, sign-up, password pages and common buttons. All three
   languages ship together.
2. **The till.** POS, cart, payment, receipts, quotes, offline indicator,
   cash drawer and customer display.
3. **Back office.** Products, inventory, purchases, returns, transfers,
   suppliers, expenses, employees, invoices, dashboard and reports,
   settings, and This device.
4. **Server and desktop.** Translated API messages and emails, the business
   language for documents, the installer and the setup page.
5. **Review.** A native speaker checks `pt-PT` and `pt-BR`, especially the
   everyday shop words: till, receipt, change, cash drawer, stock. The
   translation is in one place per language, so fixes are quick.

Each step is committed and pushed, with the README updated.
